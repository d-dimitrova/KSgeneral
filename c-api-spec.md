# Conclusion

To make `KSgeneral` usable from C/Python without R, the appropriate approach is to **avoid calling the existing R package shared library directly with `ctypes` and instead add an independent shared library whose numerical core has been separated from Rcpp**.

The recommended architecture is:

```text
R functions ── Rcpp adapter ─┐
                             ├── Pure C++ numerical core ── FFTW3
C language ── Stable C ABI ──┤
Python ctypes ────────────────┘
```

The current public CRAN version of `KSgeneral` is 2.0.2 and depends on Rcpp and FFTW3. Its existing exported symbols are Rcpp/`.Call` wrappers that accept `SEXP` values; they are not intended to be called directly without initializing the R runtime. ([CRAN][1])

# 1. How the Current Implementation Breaks Down

## Two-Sample KS/Kuiper Side

The two-sample side already has a structure that is relatively easy to separate. Its internal function accepts integers, `double` values, raw pointers, and array lengths, as shown below.

```cpp
double ks2sample_c_cpp(
    int nx, int ny, int kind,
    int M[], int lengthM,
    double q,
    double w_vec[], int lengthw,
    double tol);
```

The Rcpp wrapper merely passes `.begin()` from `Rcpp::IntegerVector` and `Rcpp::NumericVector` to the internal function. Therefore, **by moving the Rcpp portion into a separate file, the numerical core can be made standalone with relatively minor changes**. ([GitHub][2])

However, the processing performed by the high-level `KS2sample(x, y, ...)` function is not included in the C++ core. The R side performs the following:

* Removal of `NA` values
* Sorting and merging of the two samples
* Generation of multiplicities `M` for tied values
* Generation of the weight vector
* Calculation of the observed statistic
* Transformation of `kind` according to `less`/`greater` and the relative sample sizes
* Multiplicity replacement in conservative mode

Therefore, a distinction must be made between a “low-level API that accepts precomputed `M`, `q`, and `weights`” and a “high-level API that accepts raw samples `x` and `y`.” ([GitHub][3])

Also, the `_c` in the existing function names **does not mean C ABI**. `KS2sample_c_Rcpp` itself is an Rcpp `.Call` entry point and is documented as a function that calculates the complementary probability. The new API should not reuse `_c`; instead, it should explicitly state `cdf`, `ccdf`, `P(D < q)`, or `P(D >= q)`. ([GitHub][4])

## One-Sample KS Side

The one-sample side requires more extensive modification.

Currently, the R side creates boundary arrays, writes them to a fixed-name file:

```text
Boundary_Crossing_Time.txt
```

and then calls C++, which reads that file. This mechanism is actually used in both the continuous- and discrete-distribution paths. ([GitHub][5])

This approach has the following problems:

* It depends on the current working directory.
* Parallel calls within the same process conflict.
* Multiple processes using the same directory can race.
* It is unnatural for a Python library.
* File I/O becomes a hidden side effect of the numerical API.

Therefore, the boundary values should be passed as array arguments rather than through a file, using a design such as:

```cpp
double boundary_crossing_probability(
    int n,
    const double* g_steps,
    std::size_t g_count,
    const double* h_steps,
    std::size_t h_count,
    bool use_fft);
```

One point requiring caution is that the public code writes two lines in the order `f_b`, `f_a` on the R side, while the reader names the first line `lower_bound_steps` and the second line `upper_bound_steps`. This does not necessarily indicate a computational error, but it would be dangerous to change the array order based solely on the variable names. First, convert the “current first line and second line” directly into arrays, then determine their meaning and order through regression tests. ([GitHub][6])

# 2. Recommended Library Structure

The following structure is manageable during the initial phase:

```text
KSgeneral/
├── include/
│   └── ksgeneral/
│       └── ksgeneral.h       # Public C ABI
├── src/
│   ├── k2sample_core.cpp     # R-independent
│   ├── kuiper_core.cpp       # R-independent
│   ├── noncrossing_core.cpp  # R-independent
│   ├── fftw_wrappers.cpp     # Made R-independent
│   ├── c_api.cpp             # extern "C"
│   ├── rcpp_adapter.cpp      # Rcpp-specific
│   └── RcppExports.cpp       # Generated by Rcpp
├── python/
│   └── ksgeneral_ctypes.py
├── CMakeLists.txt            # Standalone build
├── configure.ac              # Retained for the R package
└── src/Makevars.in
```

The important point is that **the standalone CMake target must not include `RcppExports.cpp` or `rcpp_adapter.cpp`**.

If the core is made into a separate dynamic library from the outset and the R package is made to depend on it, installation layout and `rpath` handling become more complicated on CRAN. The following approach is safer for the initial implementation:

* The standalone version embeds the core into `libksgeneral.so` as a PIC static/object library.
* The R package version compiles the same sources using the R build system.
* The numerical-core sources are shared, but the runtime shared libraries remain separate.

The resulting artifacts would generally be:

```text
Linux:   libksgeneral.so
macOS:   libksgeneral.dylib
Windows: ksgeneral.dll
```

The R package’s `KSgeneral.so`/`KSgeneral.dll` remains R-specific.

# 3. C ABI Design

## Do Not Expose the C++ ABI Directly

The following must not be included in the public API:

* `std::vector`
* `std::string`
* C++ classes
* C++ exceptions
* Compiler-dependent mangled function names
* `Rcpp::*`
* `SEXP`

The public boundary should contain only `extern "C"`, fixed-width integers, pointers, array lengths, and status codes.

## Example Header

```c
#ifndef KSGENERAL_H
#define KSGENERAL_H

#include <stddef.h>
#include <stdint.h>

#if defined(_WIN32)
#  if defined(KSG_BUILD_DLL)
#    define KSG_API __declspec(dllexport)
#  elif defined(KSG_USE_DLL)
#    define KSG_API __declspec(dllimport)
#  else
#    define KSG_API
#  endif
#  define KSG_CALL __cdecl
#else
#  define KSG_API __attribute__((visibility("default")))
#  define KSG_CALL
#endif

#ifdef __cplusplus
extern "C" {
#endif

typedef int32_t ksg_status_t;
typedef int32_t ksg_alternative_t;
typedef int32_t ksg_probability_t;

enum {

    KSG_EINVAL    = 1,
    KSG_ERANGE    = 2,
    KSG_ENUMERIC  = 3,
    KSG_ENOMEM    = 4,
    KSG_EINTERNAL = 5
};

    KSG_ALT_TWO_SIDED = 1,
    KSG_ALT_GREATER   = 2,
    KSG_ALT_LESS      = 3
};

/* The distinction between < and >= is important for discontinuous distributions */
enum {
    KSG_PROB_LT = 1,  /* P(T < q)  */

};

KSG_API uint32_t KSG_CALL
ksg_abi_version(void);

ksg_version_string(void);

/*
 * Copies the most recent error message for the current thread.
 * The return value is the required number of characters,
 * excluding the terminating NUL.
 */
KSG_API size_t KSG_CALL
ksg_last_error(char* buffer, size_t capacity);

/*
 * Low-level two-sample KS API.
 *
 * multiplicities:
 *   Number of occurrences of each unique value in the pooled sample.
 *   Every value must be > 0, and their sum must equal m + n.
 *
 * weights:
 *   In principle, its length is m + n - 1.
 */
KSG_API ksg_status_t KSG_CALL
ksg_ks2_probability_summary(
    int32_t m,

    const double* weights,

    int32_t m,
    int32_t n,
    const int32_t* multiplicities,
    size_t multiplicity_count,
    double statistic,
    ksg_probability_t probability_type,
    double* out_probability);

/*

 * The exact boundary conventions for g_steps/h_steps
 * must be fixed in the API specification.
 */
KSG_API ksg_status_t KSG_CALL

    int32_t n,
    const double* g_steps,
    size_t g_count,
    const double* h_steps,
    size_t h_count,
    int32_t use_fft,
    double* out_probability);

/* High-level convenience API for continuous distributions */

    int32_t n,

#endif

#endif
```

## Reasons for This Design

### Do Not Return the Probability as the Function Return Value

The current two-sample code returns negative values such as `-1`, `-2`, and `-3` to indicate errors. This multiplexes probabilities and errors into the same `double`, which is unsuitable for an external API. ([GitHub][2])

The C ABI should separate them as follows:

```text
Function return value = ksg_status_t
Calculated result     = double* out_probability
Detailed error        = ksg_last_error()
```

On failure, set `*out_probability = NAN`.

### Do Not Allow Exceptions to Cross the ABI Boundary

The C API implementation should always be `noexcept` and catch all exceptions.

```cpp
extern "C"
ksg_status_t KSG_CALL
ksg_continuous_ks_ccdf(
    int32_t n,
    double q,
    double* out_probability) noexcept
{
    if (out_probability == nullptr) {
        return set_error(KSG_EINVAL, "out_probability is null");
    }

    *out_probability = NAN;

    try {
        if (n <= 0) {
            return set_error(KSG_ERANGE, "n must be positive");
        }
        if (!std::isfinite(q) || q < 0.0 || q > 1.0) {
            return set_error(KSG_ERANGE, "q must be in [0, 1]");
        }

        const double p = ksg::continuous_ks_ccdf(n, q);

        if (!std::isfinite(p)) {
            return set_error(KSG_ENUMERIC,
                             "calculation produced a non-finite value");
        }

        *out_probability = p;
        return KSG_OK;
    }
    catch (const std::bad_alloc&) {
        return set_error(KSG_ENOMEM, "memory allocation failed");
    }
    catch (const std::exception& e) {
        return set_error(KSG_EINTERNAL, e.what());
    }
    catch (...) {
        return set_error(KSG_EINTERNAL, "unknown native exception");
    }
}
```

# 4. Required Changes to the Numerical Core

## 4.1 Completely Remove Rcpp

Remove the following from the numerical core:

```cpp
#include <Rcpp.h>
using namespace Rcpp;
Rcpp::Rcout
Rcpp::Rcerr
```

In the public code, `Rcpp::Rcout`/`Rcpp::Rcerr` also remain in the boundary-crossing processing and FFTW wrappers. Replace them with error codes, internal exceptions, or a logging callback. A numerical library should also avoid writing automatically to standard output. ([GitHub][7])

## 4.2 Replace `new[]`/`delete[]` with RAII

The current two-sample code contains paths that allocate arrays with `new[]`, validate the input afterward, and return immediately on validation errors. Memory is not released on these paths. Early returns caused by numerical instability carry the same risk. ([GitHub][2])

For example, replace:

```cpp
double* P = new double[nx + 2]();
double* Q = new double[nx + 2]();
```

with:

```cpp
std::vector<double> P(static_cast<size_t>(nx) + 2, 0.0);
std::vector<double> Q(static_cast<size_t>(nx) + 2, 0.0);
```

Input validation should also be performed before allocation wherever possible.

## 4.3 Make Inputs `const`

In the current code, arrays that are not actually modified are still represented by non-`const` pointers:

```cpp
int M[]
double w_vec[]
```

Change them in the internal core to:

```cpp
const int* multiplicities
const double* weights
```

## 4.4 Integer Conversion at the Public Boundary

The C ABI uses `int32_t`, while the existing internal code uses `int`, so conversions should be explicit:

```cpp
if (multiplicity_count > static_cast<size_t>(INT_MAX)) {
    return KSG_ERANGE;
}

std::vector<int> native_multiplicities;
native_multiplicities.reserve(multiplicity_count);

for (size_t i = 0; i < multiplicity_count; ++i) {
    if (multiplicities[i] <= 0) {
        return KSG_ERANGE;
    }
    native_multiplicities.push_back(
        static_cast<int>(multiplicities[i]));
}
```

Avoid `reinterpret_cast<const int*>(multiplicities)`. Even if the types appear to have the same size on a given platform, it is safer not to encode that assumption into the public ABI.

## 4.5 Do Not Depend on `assert`

An `assert` failure inside a shared library can terminate the entire Python process. Every condition that could result from external input should be converted into normal validation:

```cpp
if (size > input_size) {
    throw std::invalid_argument("FFT input exceeds allocated size");
}
```

Assertions may remain for internally unreachable states, but they should not be used to validate user input.

# 5. Specific Separation of the One-Sample Side

First split the current implementation:

```cpp
double cont_ks_distribution(long n) {
    auto bounds =
        read_boundaries_file("Boundary_Crossing_Time.txt");

    return 1.0 - ecdf_noncrossing_probability(...);
}
```

into the following two layers:

```cpp
namespace ksg {

double one_sample_boundary_crossing_probability(
    int n,
    const std::vector<double>& g_steps,
    const std::vector<double>& h_steps,
    bool use_fft)
{
    return 1.0 -
        ecdf_noncrossing_probability(
            n, g_steps, h_steps, use_fft);
}

double continuous_ks_ccdf(int n, double q)
{
    std::vector<double> row0(static_cast<size_t>(n));
    std::vector<double> row1(static_cast<size_t>(n));

    for (int i = 1; i <= n; ++i) {
        row0[i - 1] =
            std::min(1.0, (i - 1.0) / n + q);

        row1[i - 1] =
            std::max(0.0, i / static_cast<double>(n) - q);
    }

    return one_sample_boundary_crossing_probability(
        n, row0, row1, true);
}

}
```

However, the continuous-distribution R code contains short-circuit conditions that immediately return 0 or 1 for certain values of `n` and `q`. If full compatibility with the R version is required, those conditions should also be ported in the same order. ([GitHub][5])

## Discrete- and Mixed-Distribution APIs

The R discrete-distribution API accepts a `stepfun`, while the mixed-distribution API handles user-defined CDFs and jump points. Exposing these directly as C callbacks creates the following issues, particularly with `ctypes`:

* Python callback lifetime management
* Reacquisition of the GIL
* Exception handling inside callbacks
* Cross-language call overhead at every boundary point
* Conventions for left and right limits of the CDF

Therefore, the initial API should avoid callbacks and instead use one of the following approaches:

1. The caller creates and passes `g_steps` and `h_steps`.
2. The caller passes sorted support points and arrays containing the left and right CDF values.
3. The Python wrapper evaluates the Python function and makes only one final call to the native function.

Example:

```c
ksg_status_t ksg_discrete_ks_ccdf_table(
    int32_t n,
    double q,
    const double* support,
    const double* cdf_left,
    const double* cdf_right,
    size_t support_count,
    double* out_probability);
```

This is more reproducible and easier to debug than a C callback.

# 6. Python `ctypes` Wrapper

On the Python side, `argtypes` and `restype` must always be specified. Otherwise, `ctypes` assumes an `int` return value by default, creating a risk of calling the function with incorrect types. ([Python documentation][8])

```python
from __future__ import annotations

import ctypes
from ctypes import (
    POINTER,
    byref,
    c_char,
    c_double,
    c_int32,
    c_size_t,
    c_uint32,
)
from pathlib import Path
from typing import Sequence


KSG_OK = 0

KSG_ALT_TWO_SIDED = 1
KSG_ALT_GREATER = 2
KSG_ALT_LESS = 3

KSG_PROB_LT = 1
KSG_PROB_GE = 2


class KSGeneralError(RuntimeError):
    pass


class KSGeneral:
    def __init__(self, library_path: str | Path) -> None:
        self._lib = ctypes.CDLL(str(library_path))
        self._configure_prototypes()

    def _configure_prototypes(self) -> None:
        self._lib.ksg_abi_version.argtypes = []
        self._lib.ksg_abi_version.restype = c_uint32

        self._lib.ksg_last_error.argtypes = [
            POINTER(c_char),
            c_size_t,
        ]
        self._lib.ksg_last_error.restype = c_size_t

        self._lib.ksg_ks2_probability_summary.argtypes = [
            c_int32,                    # m
            c_int32,                    # n
            c_int32,                    # alternative
            POINTER(c_int32),           # multiplicities
            c_size_t,                   # multiplicity_count
            c_double,                   # statistic
            POINTER(c_double),          # weights
            c_size_t,                   # weight_count
            c_double,                   # tolerance
            c_int32,                    # probability_type
            POINTER(c_double),          # output
        ]
        self._lib.ksg_ks2_probability_summary.restype = c_int32

    def _last_error(self) -> str:
        required = self._lib.ksg_last_error(None, 0)
        if required == 0:
            return "native calculation failed"

        buffer = ctypes.create_string_buffer(required + 1)
        self._lib.ksg_last_error(buffer, len(buffer))
        return buffer.value.decode("utf-8", errors="replace")

    def ks2_probability_summary(
        self,
        m: int,
        n: int,
        alternative: int,
        multiplicities: Sequence[int],
        statistic: float,
        weights: Sequence[float],
        *,
        tolerance: float = 1e-8,
        probability_type: int = KSG_PROB_GE,
    ) -> float:
        m_array = (c_int32 * len(multiplicities))(
            *multiplicities
        )
        w_array = (c_double * len(weights))(*weights)
        result = c_double()

        status = self._lib.ksg_ks2_probability_summary(
            c_int32(m),
            c_int32(n),
            c_int32(alternative),
            m_array,
            c_size_t(len(multiplicities)),
            c_double(statistic),
            w_array,
            c_size_t(len(weights)),
            c_double(tolerance),
            c_int32(probability_type),
            byref(result),
        )

        if status != KSG_OK:
            raise KSGeneralError(self._last_error())

        return result.value
```

In a NumPy-based version, always verify the following:

```python
M = numpy.ascontiguousarray(M, dtype=numpy.int32)
W = numpy.ascontiguousarray(W, dtype=numpy.float64)
```

The arrays must remain alive until the native function returns. The native side should not retain the pointers for later use.

# 7. Thread Safety

## Eliminate the Fixed File

Removing `Boundary_Crossing_Time.txt` eliminates at least the file-name collision problem.

## Serialize FFTW Planner Operations

In the current code, construction of an FFT executor calls `fftw_plan_dft_r2c_1d`/`fftw_plan_dft_c2r_1d`, while destruction calls `fftw_destroy_plan`. Executors are also created lazily according to the input size. ([GitHub][9])

The official FFTW documentation states that, in general, only the `fftw_execute` family is thread-safe; planner operations and other functions must be called by only one thread at a time. ([FFTW][10])

Therefore, at minimum, plan creation and destruction should be protected by a global mutex:

```cpp
namespace {

std::mutex fftw_planner_mutex;

fftw_plan create_r2c_plan(
    int n,
    double* input,
    fftw_complex* output)
{
    std::lock_guard<std::mutex> lock(fftw_planner_mutex);

    return fftw_plan_dft_r2c_1d(
        n, input, output, FFTW_ESTIMATE);
}

void destroy_plan(fftw_plan plan)
{
    if (plan == nullptr) {
        return;
    }

    std::lock_guard<std::mutex> lock(fftw_planner_mutex);
    fftw_destroy_plan(plan);
}

}
```

`fftw_execute` does not need to be serialized, provided each call uses independent buffers and plans.

If safety is the priority in the initial release, it is acceptable to serialize the entire one-sample FFT calculation with a mutex. After adding tests, the critical section can be narrowed to planner operations only.

Python’s `ctypes.CDLL` releases the GIL during native function calls, so the Python GIL must not be treated as an implicit lock. ([Python documentation][8])

# 9. How Much of the High-Level API Should Be Ported to C++?

## Recommended Two-Stage Design

### Stage 1: Numerical-Kernel API

Initially expose the following:

```text
ksg_ks2_probability_summary
ksg_kuiper2_probability_summary
ksg_one_sample_boundary_probability
ksg_continuous_ks_ccdf
ksg_abi_version
ksg_last_error
```

This configuration requires relatively few changes to the existing algorithms and makes numerical comparison with the R version straightforward.

### Stage 2: Raw-Sample API

Then add:

```c
typedef struct ksg_test_result {
    uint32_t struct_size;
    double statistic;
    double p_value;
} ksg_test_result;

ksg_status_t ksg_ks2_test(
    const double* x,
    size_t x_count,
    const double* y,
    size_t y_count,
    ksg_alternative_t alternative,
    int32_t conservative,
    const double* weights,
    size_t weight_count,
    double tolerance,
    ksg_test_result* result);
```

Placing `struct_size` first makes it easier to append fields later while preserving backward compatibility.

To preserve compatibility with the R version, the raw-sample API must specify at least the following:

* Whether `NaN` values are removed or treated as errors
* Equality of `+0.0` and `-0.0`
* Handling of `Inf`
* Tie-detection rules
* Direction of `less`/`greater`
* Direction transformation when sample sizes are swapped
* Conservative mode
* Weight evaluation points
* The distinction between `P(T >= t)` and `P(T > t)`

It is safer initially to accept a pre-evaluated weight vector rather than a C callback for the weight function.

# 10. Regression-Test Strategy

Before modification, pin the reference version. Use CRAN 2.0.2 or a specific Git commit rather than relying solely on the mutable `master` branch.

## Minimum Required Tests

### Two-Sample KS

* Without ties
* With ties
* `two.sided`
* `less`
* `greater`
* Sample sizes with `m < n` and `m > n`
* No weighting
* Default weighting
* Arbitrary weight vector
* With and without conservative mode
* Near `q = 0`
* Near `q = 1`
* `P(D < q)` and `P(D >= q)`

### Kuiper

* With and without ties
* `q = 0`
* Near `q = 2`
* Sample sizes with different greatest common divisors
* Overflow detection

### One-Sample

* Continuous distribution
* Discrete distribution
* Mixed distribution
* `n = 1`
* `q = 0`
* `q = 1`
* Cases that trigger R-side short-circuit conditions
* Cases using FFT
* Small cases using naive convolution

### Tests for Removing the Boundary File

1. Save the two lines written by the pre-modification code.
2. Call the old file-based function.
3. Pass the same two lines to the new array API.
4. Compare the results.
5. Only then finalize the names `g`/`h` and lower/upper.

### Robustness

* Null pointers
* Mismatched array lengths
* `sum(M) != m + n`
* `M[i] <= 0`
* Non-positive weights
* `NaN`
* `Inf`
* Integer overflow
* Very large `n`
* Simulated out-of-memory conditions
* Concurrent calls from multiple Python threads

### Tools

* AddressSanitizer
* UndefinedBehaviorSanitizer
* Valgrind
* Windows Application Verifier
* CI on Linux/macOS/Windows
* ABI smoke tests from a pure C program
* Smoke tests from Python `ctypes`

Comparison tolerances should not be uniform. Use strict relative and absolute tolerances for ordinary cases, and separate tolerances for FFT paths and extreme tails.

# 11. Implementation Order

1. **Pin the reference version and create golden tests from the R output.**
2. **Remove Rcpp from the two-sample core.**
3. **Replace `new[]` with RAII and separate negative-value errors into internal status values.**
4. **Replace one-sample file input with array input.**
5. **Remove `Rcpp::Rcout/Rcerr` and assertions that depend on external input.**
6. **Add the C ABI.**
7. **Add the standalone CMake build.**
8. **Add C smoke tests.**
9. **Add the Python `ctypes` wrapper.**
10. **Add FFTW planner locking and concurrency tests.**
11. **Gradually port the raw-sample API and high-level APIs for discrete and mixed distributions.**

# Recommended Initial Milestone

The lowest-risk initial version is:

```text
R version:
    Preserve the existing R API.
    Call the pure C++ core through the Rcpp adapter.

C version:
    Low-level two-sample API accepting M, weights, and the statistic.
    One-sample API accepting boundary arrays.
    Continuous-distribution API accepting n and q.

Python version:
    Thin wrapper using ctypes.
    Initially perform raw-sample sorting, tie handling,
    and weight generation on the Python side.
```

This achieves the following without substantially changing the core algorithms:

* Independence from the R runtime
* A stable C ABI
* `ctypes` support
* Elimination of file I/O
* Support for concurrent calls
* Compatibility with the existing R version

A complete high-level API accepting raw samples directly, along with native implementations for discrete and mixed CDFs, should be treated as a separate compatibility phase afterward.
